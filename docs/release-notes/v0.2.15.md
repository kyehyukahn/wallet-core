# v0.2.15 — Android JNI loadLibrary in WalletCoreModule

Patch release. Android-only fix. The TypeScript surface, iOS native
bridge, error messages, proto shapes, and supported coin set are all
**identical to v0.2.14**.

## Why this release

Reported by the cirqle-mobile native dev. v0.2.14 Android
`assembleDebug` was green and the consumer APK installed + launched
cleanly, but the first `WalletCoreModule.deriveAddress` call from JS
threw at runtime:

```
java.lang.UnsatisfiedLinkError: No implementation found for
  long wallet.core.jni.HDWallet.nativeCreateWithMnemonic(java.lang.String, java.lang.String)
  (tried Java_wallet_core_jni_HDWallet_nativeCreateWithMnemonic ...)
  - is the library loaded, e.g. System.loadLibrary?
```

### Root cause

`wallet-core.aar` ships `libTrustWalletCore.so` for every Android ABI
(arm64-v8a / armeabi-v7a / x86 / x86_64) under `jni/<abi>/`. AGP
repacks them into the consumer APK's `lib/<abi>/`. But **zero**
classes inside `classes.jar` call `System.loadLibrary("TrustWalletCore")`
— verified across the full `classes.jar` table-of-contents via
`javap -c | grep loadLibrary`. The .so is on disk; nothing tells the
JVM to load it.

iOS doesn't have a symmetric class because Apple's static linker
resolves the xcframework's symbols at link time. JNI on Android
requires an explicit JVM-side load.

### Why Stage B (compile) passed but Stage D (runtime) failed

`assembleDebug` validates that Kotlin/Java compiles and JNI
declarations link correctly at the **bytecode-symbol** level. It does
not execute the JVM. The missing `loadLibrary` is an init-time bug —
it surfaces only the first time `HDWallet`, `Mnemonic`, `CoinType`,
etc. is instantiated. cirqle's Stage D smoke is the first JVM
execution; that's where the regression became visible.

## What changed

| File | Change |
|---|---|
| `npm-package/android/src/main/java/expo/modules/walletcore/WalletCoreModule.kt` | adds a `companion object { init { System.loadLibrary("TrustWalletCore") } }` block. Runs once when the JVM resolves the class, which is during Expo Modules autolinking at app startup — well before any JS call reaches a JNI method. |
| `npm-package/package.json` | `version` 0.2.14 → 0.2.15. |
| `tools/release-pack` | **new pack-time invariant guard.** Greps `WalletCoreModule.kt` for `System.loadLibrary(...)"TrustWalletCore"`; bails with `exit 10` if missing. The fifth pack-time guard, paired with the four iOS guards from v0.2.2 / v0.2.3 / v0.2.4 / v0.2.5. Catches B10-class regressions at pack time without needing to run a JVM. |
| Native xcframeworks / AAR / proto JAR / swift-sources tarball | **content unchanged from v0.2.14**. Pure Kotlin-wrapper patch over the same native artifacts. |

## Consumer migration: v0.2.14 → v0.2.15

```bash
pnpm add @kyehyukahn/wallet-core@^0.2.15
pnpm exec expo prebuild --clean
pnpm android
```

Drop-in. No code change on the consumer side. No TS API change. No
iOS rebuild needed — the iOS slice of the package is byte-identical to
v0.2.14 (no Swift change). Re-running iOS prebuild is a no-op.

## Verification

- `grep -n "System.loadLibrary" npm-package/android/src/main/java/expo/modules/walletcore/WalletCoreModule.kt` reports the new line.
- `tools/release-pack 0.2.15` passes the new invariant guard:
  `OK (System.loadLibrary call present)`.
- `tools/release-pack 0.2.15` with the line removed (negative-test)
  exits with `ERROR: ... does not call System.loadLibrary(...)`.

Consumer-side `xcodebuild` / `pnpm android` runtime validation is the
cirqle PR 3 Stage D rerun on emulator-5554.

## Pack-time invariant guards (cumulative)

1. swift-sources `.pb.swift` count > 0 (v0.2.2)
2. Ethereum/Solana/Common.pb.swift presence (v0.2.3)
3. no `WalletCoreSwiftProtobuf` reference leak (v0.2.4)
4. every TW-using `.swift` imports `WalletCoreCommon` (v0.2.5/v0.2.8)
5. xcframework slices carry `Modules/module.modulemap` + umbrella header (v0.2.5)
6. **WalletCoreModule.kt calls `System.loadLibrary("TrustWalletCore")` (v0.2.15)**

## Followups (deferred to v0.3)

- JVM smoke harness (compile + run a single `HDWallet(128, "")` test) in `tools/release-pack`. Catches the same B10 class plus any future JNI-binding mismatch. Heavier than the grep guard but symmetric with what `pod lib lint` would do for iOS.
- Move iOS post-processing (sed normalisations, modulemap injection, strip-list) into `tools/ios-build` so artifacts are correct at source time rather than patched in release-pack.
