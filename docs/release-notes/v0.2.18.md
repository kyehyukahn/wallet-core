# v0.2.18 — Android: fix `def nativeAndroidDir` lexical scope (v0.2.17 regression)

Patch release. **Same-day follow-up to v0.2.17.** A one-line block-move
in `npm-package/android/build.gradle` + a new release-pack invariant
guard. No source code change, no native binary change, no API change.

## Why this release (v0.2.17 regression)

v0.2.17 introduced `sourceSets.main.jniLibs.srcDirs += ["${nativeAndroidDir}/jniLibs"]`
**inside** the `android { ... }` block to consume the unpacked JNI libs.
AGP evaluates that closure eagerly during the configuration phase, so
the GString interpolation reads `nativeAndroidDir` from script-scope at
that moment. But the `def nativeAndroidDir = …` declaration kept its
v0.2.16 position — **below** the `android { ... }` block, because back
then only the lazily-evaluated `dependencies { ... }` block referenced
the variable.

Net effect on a fresh consumer install (CI, other dev machines,
post-`pnpm install` cold checkouts): configuring `:kyehyukahn-wallet-core`
threw `MissingPropertyException: nativeAndroidDir`, and AGP never
finalized the release variant. expo-module-gradle-plugin's
`applyPublishing → PublicationInfo` then called
`project.components.getByName("release")` and surfaced the cascade
"SoftwareComponent with name 'release' not found", which is a red
herring that obscures the real cause.

Reproduction:

```
$ cd cirqle-mobile/apps/mobile/android && ./gradlew :kyehyukahn-wallet-core:assembleDebug --stacktrace
…
> Could not get unknown property 'nativeAndroidDir' for source set main of
  type com.android.build.gradle.internal.api.DefaultAndroidSourceSet.
Caused by: groovy.lang.MissingPropertyException: Could not get unknown property
'nativeAndroidDir' for source set main of type
com.android.build.gradle.internal.api.DefaultAndroidSourceSet.
  at expo.modules.plugin.android.PublicationInfo.<init>(MavenPublicationExtension.kt:38)
  at expo.modules.plugin.ProjectConfigurationKt.applyPublishing$lambda$3(ProjectConfiguration.kt:81)

> SoftwareComponent with name 'release' not found.
```

The AGP 8.x `hasLocalAarDeps` fix from v0.2.17 itself is sound — the
`:kyehyukahn-wallet-core:bundleDebugAar` task no longer trips on a
local-AAR file dep. This is a pure Groovy-scope ordering issue layered
on top.

## The shape of the fix (one block-move)

```diff
 def package_version = '0.2.18'

 group = 'expo.modules.walletcore'
 version = package_version

+// projectDir = node_modules/@kyehyukahn/wallet-core/android/
+// Native artifacts are downloaded by postinstall to ../native/android/.
+//
+// MUST be declared BEFORE the `android { ... }` block — AGP evaluates that
+// closure eagerly during the configuration phase and
+// sourceSets.main.jniLibs.srcDirs += ["${nativeAndroidDir}/jniLibs"]
+// reads from script-scope at that moment.
+def nativeAndroidDir = new File(projectDir.parentFile, 'native/android')
+
 android {
     namespace 'expo.modules.walletcore'
     ...
     sourceSets {
         main {
             java { srcDirs += ['src/main/java'] }
             jniLibs.srcDirs += ["${nativeAndroidDir}/jniLibs"]
         }
     }
 }

-// projectDir = node_modules/@kyehyukahn/wallet-core/android/
-// Native artifacts are downloaded by postinstall to ../native/android/.
-def nativeAndroidDir = new File(projectDir.parentFile, 'native/android')
-
 dependencies {
     implementation files("${nativeAndroidDir}/wallet-core-classes.jar")
     ...
 }
```

End-to-end verified on dev-native @ `5dc56f3` + PR 5a-2 storage stack
on a `pnpm install` of v0.2.18 (no manual node_modules patching):
`:app:assembleDebug BUILD SUCCESSFUL in ~2-3m` → 255 MB debug APK.

## release-pack invariant guard #13

Pattern-match guards #11/#12 from v0.2.17 only verified content
correctness (the dep replaced, the unzip step present). They had no way
to know about closure evaluation order. New guard runs line-number
comparison:

```bash
DEF_LINE=$(grep -n '^def nativeAndroidDir\b' npm-package/android/build.gradle | head -1 | cut -d: -f1)
ANDROID_LINE=$(grep -n '^android[[:space:]]*{' npm-package/android/build.gradle | head -1 | cut -d: -f1)
JNI_REF_LINE=$(grep -n 'jniLibs\.srcDirs.*nativeAndroidDir' npm-package/android/build.gradle | head -1 | cut -d: -f1)
# Guard fails if:
#   - def missing
#   - android { } missing
#   - def comes after the jniLibs reference site
#   - def comes after the android { } block opens
```

Pair with the convention: every script-scope `def` lives above the
`android { ... }` block. Mechanical, cheap, scales to future intra-
closure references.

## Long-term cleanup (deferred)

The `npm-package/android/build.gradle` literal `def package_version`
(currently bumped manually per release) is independent of the lexical
ordering issue but worth revisiting alongside; either parse from
`package.json` at configure time, or land a CI-side bump check that
diffs the two. Not urgent — `release-pack` only checks AAR/dep patterns,
not version strings.
