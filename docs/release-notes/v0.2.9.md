# v0.2.9 — strip CryptoBox cascade + fix AnySigner.sign generic call

iOS + (cosmetic) Android patch over v0.2.8. The shipped `swift-sources.tar.gz` now excludes the full CryptoBox family; the iOS chain signing helpers (`EvmSigning.swift`, `SolanaSigning.swift`) call the correct upstream `AnySigner.sign<Output>(input:coin:)` generic.

## What was broken

### 1. CryptoBox cascade after v0.2.8 strip

v0.2.8 stripped `CryptoBoxSecretKey.swift` because its `TWCryptoBoxSecretKeyGetPublicKey` reference was missing from the shipped C headers. v0.2.8 xcodebuild then surfaced the dependents:

```
.../Sources/Generated/CryptoBox.swift:22:46: error: cannot find type 'CryptoBoxSecretKey' in scope
.../Sources/Generated/CryptoBoxPublicKey.swift:23:16: error: cannot find 'TWCryptoBoxPublicKeyIsValid' in scope
.../Sources/Generated/CryptoBoxPublicKey.swift:45:30: error: cannot find 'TWCryptoBoxPublicKeyCreateWithData' in scope
.../Sources/Generated/CryptoBoxPublicKey.swift:52:9: error: cannot find 'TWCryptoBoxPublicKeyDelete' in scope
```

- `CryptoBox.swift` references the stripped `CryptoBoxSecretKey` type
- `CryptoBoxPublicKey.swift` itself has the same codegen-vs-header drift on three more symbols

The whole CryptoBox family is now skipped from the tarball.

### 2. iOS EvmSigning / SolanaSigning calling AnySigner.sign with the wrong signature

```
.../ios/chains/EvmSigning.swift:57:33: error: generic parameter 'SigningOutput' could not be inferred
.../ios/chains/EvmSigning.swift:57:37: error: incorrect argument label in call (have 'data:coin:', expected 'input:coin:')
.../ios/chains/EvmSigning.swift:57:44: error: argument type 'Data' does not conform to expected type 'Message'
```

Our `EvmSigning.swift` (and `SolanaSigning.swift`) was calling:

```swift
let outputBytes = AnySigner.sign(data: try input.serializedData(), coin: .ethereum)
let output = try TW_Ethereum_Proto_SigningOutput(serializedData: outputBytes)
```

The upstream `AnySigner.sign` is generic over the SigningOutput SwiftProtobuf message and takes the input SigningInput directly (not pre-serialized bytes):

```swift
public static func sign<SigningOutput: Message>(input: SigningInput, coin: CoinType) -> SigningOutput
```

This was an original-scaffold guess (the Kotlin / Java side of AnySigner takes raw bytes, which we mirrored on iOS by mistake) that survived because B2~B7 prevented xcodebuild from reaching the chain signing code.

The Kotlin equivalent (`EvmSigning.kt`, `SolanaSigning.kt`) is **correct** — Java's `AnySigner.sign(byte[] input, CoinType coin)` does take raw bytes. No change needed.

## Fix

### iOS chains (npm-package/ios/chains/{EvmSigning,SolanaSigning}.swift)

```swift
// Before (v0.2.8 and earlier)
let inputBytes = try input.serializedData()
let outputBytes = AnySigner.sign(data: inputBytes, coin: .ethereum)
let output = try TW_Ethereum_Proto_SigningOutput(serializedData: outputBytes)

// After (v0.2.9)
let output: TW_Ethereum_Proto_SigningOutput =
    AnySigner.sign(input: input, coin: .ethereum)
```

The return-type annotation drives the inference of the generic `SigningOutput` parameter. Cleaner code, no manual serialization.

### release-pack SWIFT_SKIP list expansion

```bash
SWIFT_SKIP=(
    "Sources/Generated/CryptoBox.swift"
    "Sources/Generated/CryptoBoxPublicKey.swift"
    "Sources/Generated/CryptoBoxSecretKey.swift"
)
```

Whole family stripped. None used by EVM / Solana signing or anything else on the cirqle path.
