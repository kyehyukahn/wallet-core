# v0.2.17 — Android: split wallet-core.aar into classes.jar + jniLibs (AGP 8.x safe)

Patch release. **Build-system-only fix.** No source code change, no native
binary change, no API change. The TypeScript surface, native bridge,
error messages, proto shapes, supported coin set, and every fix from
v0.2.13 → v0.2.16 are carried forward unchanged.

## Why this release (B11)

Consumer Stage B (`./gradlew :app:assembleDebug` via `pnpm android`) on
AGP 8.x failed during cirqle-mobile PR 5a-2 verification:

```
FAILURE: Build failed with an exception.
* What went wrong:
Execution failed for task ':kyehyukahn-wallet-core:bundleDebugAar'.
> Error while evaluating property 'hasLocalAarDeps' of task ':kyehyukahn-wallet-core:bundleDebugAar'.
   > Direct local .aar file dependencies are not supported when building an AAR.
     The resulting AAR would be broken because the classes and Android resources
     from any local .aar file dependencies would not be packaged in the resulting AAR.
     The following direct local .aar file dependencies of the :kyehyukahn-wallet-core
     project caused this error:
     .../@kyehyukahn/wallet-core/native/android/wallet-core.aar
```

AGP 8.x runs `bundleDebugAar` eagerly on every `android-library` module
— including this one — and `hasLocalAarDeps` refuses the long-standing
pattern v0.1.0 → v0.2.16 shipped:

```gradle
// v0.2.16 npm-package/android/build.gradle (rejected)
dependencies {
    implementation files("${nativeAndroidDir}/wallet-core.aar")
    implementation files("${nativeAndroidDir}/wallet-core-proto.jar")
    ...
}
```

The wrap-library AAR (the one expo-module-gradle-plugin produces for
this module) would silently lose the wallet.core classes + JNI .so from
the embedded `wallet-core.aar`, so AGP refuses to build it. Note: `:app`
consumes wallet-core as a project dep so `:kyehyukahn-wallet-core:
bundleDebugAar`'s output is never actually used — but AGP evaluates the
task graph regardless. No workaround on the consumer side; the fix has
to land here.

## The shape of the fix

The shipped `wallet-core.aar` (29 MB) has only:

```
$ unzip -l native/android/wallet-core.aar
    0    R.txt                                      ← empty
  193    AndroidManifest.xml                        ← stub
87828    classes.jar
    0    jni/arm64-v8a/
17 MB    jni/arm64-v8a/libTrustWalletCore.so
12 MB    jni/armeabi-v7a/libTrustWalletCore.so
20 MB    jni/x86/libTrustWalletCore.so
19 MB    jni/x86_64/libTrustWalletCore.so
```

No `res/`, no aidl, no components, no proguard. The AAR container exists
only for delivery — there's nothing in it that requires the AAR shape at
build time. So we split it back into the two AGP-native inputs:

1. **`postinstall.js`** (new step): after the AAR downloads, `unzip` it
   in place — rename `classes.jar` → `wallet-core-classes.jar`, move
   `jni/` → `jniLibs/`, leave the original `.aar` on disk as a
   debuggability artifact (not a build input).

2. **`android/build.gradle`** (replaced two lines): consume the unpacked
   pair instead of the AAR container.

   ```gradle
   // v0.2.17 npm-package/android/build.gradle
   sourceSets {
       main {
           ...
           jniLibs.srcDirs += ["${nativeAndroidDir}/jniLibs"]
       }
   }
   dependencies {
       implementation files("${nativeAndroidDir}/wallet-core-classes.jar")
       implementation files("${nativeAndroidDir}/wallet-core-proto.jar")
       implementation 'com.google.protobuf:protobuf-javalite:3.22.3'
   }
   ```

`implementation files(...classes.jar)` is a plain local JAR dep — AGP
does not trip `hasLocalAarDeps` on JARs. `jniLibs.srcDirs += [...]` is
the canonical AGP path for shipping `.so` libs into the merged APK;
Gradle bundles them exactly the way `wallet-core.aar` did. Net APK
content is unchanged.

### Consumer impact

**Zero.** Re-running `pnpm install` triggers the new postinstall, which
re-lays out `native/android/`, and the build just works. No code change
in cirqle-mobile, no plugin add, no autolink reshuffle.

## release-pack invariant guards (B11.guard)

`tools/release-pack` now refuses to package a release that regresses
this fix:

1. `npm-package/android/build.gradle` must NOT reference
   `wallet-core.aar` as an `implementation files(...)` dep.
2. `npm-package/android/build.gradle` MUST declare
   `wallet-core-classes.jar` + `jniLibs.srcDirs` extension.
3. `npm-package/postinstall.js` MUST contain an `unzip` step for
   `wallet-core.aar` and emit `wallet-core-classes.jar`.

Same shape as the iOS pack-time guards (`.pb.swift` count,
Ethereum/Solana presence, `WalletCoreSwiftProtobuf` leak, wrapper
Foundation-only import, `WalletCoreCommon.framework` module map) and
the v0.2.15 Android `System.loadLibrary` guard.

## Native binaries

**Content-identical to v0.2.16.** Re-packed from the same unchanged
build outputs (`swift/WalletCoreRs.xcframework`,
`build/ios-frameworks/WalletCoreCommon.xcframework`,
`build/wallet-core.aar`,
`android/wallet-core-proto/build/libs/wallet-core-proto.jar`,
`swift/Sources/`).

Per-asset SHA256 vs v0.2.16:

| Asset | byte-identical? | Why |
|---|---|---|
| `wallet-core.aar` | yes | plain file copy |
| `wallet-core-proto.jar` | yes | plain file copy |
| `WalletCoreCommon.xcframework.zip` | no | `ditto -c -k` re-pack metadata |
| `WalletCoreRs.xcframework.zip` | no | `ditto -c -k` re-pack metadata |
| `swift-sources.tar.gz` | no | `tar -czf` re-pack metadata |

Native binaries inside the (re-packed) archives are unchanged. The
postinstall verifies via `SHA256SUMS` published alongside this release,
so the SHA delta is invisible to consumers.

## What was not touched

- TypeScript surface (`src/`, `evm/`, `solana/`) — no change.
- Expo Module wrappers (iOS Swift, Android Kotlin including the v0.2.15
  `System.loadLibrary("TrustWalletCore")` companion init) — no change.
- iOS pack-time invariants — no change.
- Consumer-facing peer deps (`expo`, `expo-modules-core`,
  `react-native`) — no change.
