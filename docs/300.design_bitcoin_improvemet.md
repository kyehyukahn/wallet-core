# Bitcoin Feature Improvement Design

- **Date**: 2026-03-31
- **Status**: Revised Draft
- **Source**: breadwallet-core -> wallet-core (Rust) migration design
- **Priority**: Phase 1 Bitcoin SPV/P2P foundation -> Phase 2 Wallet Manager -> Phase 3 Transaction improvement -> Phase 4 Multi-chain expansion

---

## 1. Goal

breadwallet-core의 검증된 Bitcoin SPV 동기화 및 wallet state 관리 방식을 wallet-core의 Rust 계층으로 재구성한다.

이 설계의 목표는 다음 3가지다.

1. 중앙 서버 없이 Bitcoin 네트워크와 직접 동기화 가능한 선택적 SPV 레이어를 추가한다.
2. UTXO 추적, 주소 갭 리밋, 잔액 산출, 재스캔 등 상태ful wallet 기능을 Rust 계층으로 올린다.
3. 현재 `CoinEntry`/`TWAnySigner` 기반 서명 API를 유지하면서, 향후 BCash/Litecoin/Dogecoin 확장을 막지 않는 구조를 만든다.

---

## 2. Scope

### In Scope

- Bitcoin mainnet/testnet용 SPV 네트워크 동기화
- Bitcoin wallet state 관리
- block header / merkle proof / filtered tx 처리
- 앱이 선택적으로 사용할 수 있는 wallet manager 계층
- 기존 `tw_utxo`, `tw_bitcoin`, `CoinEntry`, `TWAnySigner`와의 통합
- 이후 BCash/Litecoin/Dogecoin 확장을 위한 명시적 abstraction point 정의

### Out of Scope For Initial Delivery

- BCash/Litecoin/Dogecoin 실제 네트워크 지원
- Electrum, Neutrino(BIP157/158), full node 모드
- Payment Protocol(BIP70/71/72) 기본 지원
- 앱 내 persistence 구현체 제공
- Bitcoin 외 체인의 난이도 규칙 및 포크별 relay 정책 구현

### Scope Principle

초기 구현의 deliverable은 **Bitcoin only**로 제한한다. 대신 설계 경계는 multi-chain 확장을 고려해 미리 분리한다. 즉, **runtime behavior는 Bitcoin 기준으로 닫고, extension surface는 일반화**한다.

---

## 3. Design Principles

### 3-1. Bitcoin First, Multi-chain Ready

- 동작 검증과 상호운용성은 Bitcoin 기준으로 먼저 확보한다.
- BCash/Litecoin/Dogecoin 지원을 위해 공통 계층을 만들되, Phase 1에서 모든 체인을 한 번에 구현하지 않는다.
- 공통화는 실제 차이가 반복되는 지점에만 적용한다.

### 3-2. Preserve Existing Signing API

- `CoinEntry`, `TWAnySigner`, `TWAnyAddress`의 기존 동작은 유지한다.
- SPV/wallet manager는 기존 signer 위에 올라가는 선택적 상위 계층이다.
- SPV를 사용하지 않는 앱은 기존 API만으로 계속 동작해야 한다.

### 3-3. Runtime Isolation

- 서명/주소 계산처럼 stateless한 기능과 네트워크 동기화처럼 stateful한 기능을 분리한다.
- `tw_utxo`는 계속 transaction/signing 중심으로 유지한다.
- 새 SPV 계층은 별도 framework crate로 추가한다.

### 3-4. Explicit Failure Model

- BIP37 지원 피어 부족, 네트워크 단절, persistence 손상, bloom filter 재구성 실패를 정상적인 운영 시나리오로 간주한다.
- 설계 문서에 fallback과 복구 동작을 명시한다.

## 5. API Positioning

### Existing API

```text
TWAnySigner -> CoinEntry::sign() -> signing only
```

### New Optional API

```text
WalletManager -> SyncManager -> PeerManager -> Bitcoin P2P sync
             -> Wallet -> tw_utxo primitives -> build/sign/broadcast
```

### Compatibility Rule

- 기존 `CoinEntry` 기반 signing flow는 변경하지 않는다.
- 새 wallet manager는 별도 API surface로 제공한다.
- 기존 앱은 migration 없이 현재 flow를 계속 사용할 수 있어야 한다.

## 6. Chain Abstraction Strategy

multi-chain을 고려하되, abstraction은 두 단계로 나눈다.

### 6-1. Stable Cross-chain Abstractions

아래 항목은 Bitcoin 계열 UTXO 체인에서 비교적 안정적으로 일반화 가능하다.

- 네트워크 식별자
- default port
- dns seed 목록
- checkpoint 목록
- protocol version policy
- address encoding family
- transaction hash / sighash variation
- difficulty verification entry point
- bloom filter capability policy

### 6-2. Chain-specific Behavior That Must Not Be Over-generalized

아래 항목은 Phase 1에서 억지로 공통화하지 않는다.

- 난이도 조정 규칙 세부
- BCH fork ID / sighash 차이
- relay policy 차이
- dust threshold 정책 차이
- 주소 prefix 및 cashaddr/bech32/base58 혼합 정책
- 체인별 checkpoint 운영 방식

### 6-3. Recommended Traits

```rust
pub trait SpvChain {
    type Utxo: UtxoContext;

    fn chain_id(&self) -> ChainId;
    fn network_magic(&self) -> u32;
    fn default_port(&self) -> u16;
    fn dns_seeds(&self) -> &'static [&'static str];
    fn checkpoints(&self) -> &'static [Checkpoint];

    fn min_protocol_version(&self) -> u32;
    fn protocol_version(&self) -> u32;

    /// Chain-level policy: 이 체인이 BIP37 bloom filtering을 사용할 수 있는 체인인지 여부.
    /// 피어 수준의 NODE_BLOOM 서비스 비트 검사는 PeerManager 내부에서 별도 수행한다.
    fn supports_bloom_filtering(&self) -> bool;
    fn verify_header_chain(
        &self,
        prev: &BlockHeader,
        current: &BlockHeader,
        height: u32,
    ) -> Result<(), HeaderVerificationError>;
}

pub trait WalletChain {
    type Utxo: UtxoContext;

    fn external_gap_limit(&self) -> u32;
    fn internal_gap_limit(&self) -> u32;
    fn dust_policy(&self, fee_rate: u64) -> u64;
    fn max_reorg_depth_hint(&self) -> u32;
}
```

### 6-4. Why Two Traits

- `SpvChain`은 네트워크와 검증 규칙에 집중한다.
- `WalletChain`은 주소 정책, dust, rescan 정책처럼 wallet state와 가까운 규칙을 맡는다.
- 두 책임을 분리하면 BCash/Litecoin/Dogecoin 지원 시 변화가 퍼지는 범위를 줄일 수 있다.

## 7. Runtime Model

문서 초안의 `tokio` 방향은 유지하되, runtime 소유권을 명확히 한다.

### 7-1. Runtime Policy

- 내부 구현은 async 기반으로 작성한다.
- 하지만 public API는 앱이 async runtime 세부를 알 필요 없도록 감싼다.
- wallet-core가 외부 앱에 `tokio`를 강제 노출하지 않는다.

### 7-2. Recommended Runtime Boundary

```rust
pub trait SpvRuntime: Send + Sync {
    fn spawn(&self, task: BoxFuture<'static, ()>);
    fn spawn_blocking(&self, task: BoxFuture<'static, ()>);
    fn now(&self) -> SystemTime;
}
```

### 7-3. Why Not Expose Tokio Directly

- wallet-core는 라이브러리이며 모바일/desktop 바인딩을 함께 가진다.
- FFI 경계 바깥으로 특정 async runtime을 강하게 노출하면 iOS/Android/desktop 통합 비용이 커진다.
- 내부 default runtime 구현은 둘 수 있지만, public design은 runtime abstraction 위에 둔다.

## 8. Phase 1: Bitcoin SPV Foundation

### Deliverable

- Bitcoin mainnet/testnet 피어 연결
- version/verack handshake
- header sync
- bloom filter 기반 filtered block sync
- merkle proof 검증
- peer/persistence 복구
- wallet manager 없이도 sync progress를 관찰할 수 있는 최소 event stream

### Not Yet In Phase 1

- BCash/Litecoin/Dogecoin 실제 연결
- multi-chain runtime test matrix
- fee estimation 개선 전부
- BIP38

### Core Components

#### Peer

책임:

- 단일 peer 연결 수명주기 관리
- message framing/parsing
- ping/pong, timeout, service bit 처리

유지할 wire behavior:

- Bitcoin message header `magic + command + length + checksum`
- `version`, `verack`, `ping`, `pong`, `inv`, `getdata`, `headers`, `merkleblock`, `tx`, `notfound`

구현 원칙:

- raw pointer arithmetic 대신 안전한 parser 사용
- read/write timeout과 protocol validation을 분리
- peer-level state machine을 명시적 enum으로 관리

#### PeerManager

책임:

- peer discovery
- peer selection
- download peer 결정
- retry/backoff
- misbehavior tracking

Phase 1 규칙:

- 최대 연결 수는 작게 유지한다
- DNS seed로 peer를 로드하되 persistence cache를 우선 사용한다
- bloom filter 지원이 없는 peer는 download peer 후보에서 제외한다

Bloom filter 지원 판단은 두 단계로 이루어진다:

1. **체인 수준**: `SpvChain::supports_bloom_filtering()` — 이 체인이 BIP37을 지원하는 체인인지 (Bitcoin: true)
2. **피어 수준**: version handshake 시 `services` 필드의 `NODE_BLOOM(0x04)` 비트 검사 — 해당 피어가 실제로 bloom filter를 지원하는지

체인이 BIP37을 지원하더라도 연결된 모든 피어가 `NODE_BLOOM`을 가지고 있지 않을 수 있다. 이 경우 `SyncCapability::HeaderOnly`로 전환한다.

#### SyncManager

책임:

- header sync -> block fetch -> filtered tx delivery 순서 제어
- earliest key time 기반 sync 범위 계산
- rescan/reconnect/recovery orchestration

## 9. BIP37 Policy And Fallback

BIP37은 Phase 1의 실용적 출발점으로 사용하지만, 장기적으로 이상적인 종착점으로 간주하지 않는다.

### 9-1. Reality

- 일부 공용 노드는 bloom filtering을 지원하지 않거나 제한적으로 지원한다.
- 프라이버시 측면에서 BIP37은 강하지 않다.
- 따라서 "BIP37만 있으면 충분하다"는 가정을 설계에 넣지 않는다.

### 9-2. Phase 1 Operational Policy

- 기본 동기화 경로는 BIP37 기반으로 구현한다.
- peer capability 검사에서 bloom filter 미지원 peer는 filtered sync에 사용하지 않는다.
- bloom filter 지원 peer를 확보하지 못하면 sync 상태를 실패로 숨기지 않고, 명시적 capability error로 표면화한다.

### 9-3. Required Fallback States

```rust
pub enum SyncCapability {
    FullBip37,
    HeaderOnly,
    Unsupported,
}
```

필수 동작:

- `FullBip37`: header + filtered block sync 수행
- `HeaderOnly`: header chain만 유지하고 wallet sync는 중단
- `Unsupported`: wallet sync 시작 불가 상태로 보고

### 9-4. Why This Matters

이 fallback을 미리 두면 나중에 Electrum 또는 Neutrino 같은 대체 백엔드를 추가할 때 `SyncCapability` 수준에서 확장할 수 있다.

### 9-5. BIP157/158 (Compact Block Filters / Neutrino) Migration Path

BIP37의 프라이버시 한계(연결된 피어가 사용자의 주소 패턴을 추론 가능)를 장기적으로 해결하기 위해, BIP157/158 기반 Compact Block Filters(Neutrino) 지원을 Phase 5+ 목표로 설정한다.

#### Phase 1에서 미리 준비할 것

1. **`SyncCapability` enum에 variant 예약**:
   ```rust
   pub enum SyncCapability {
       FullBip37,
       CompactFilters,  // BIP157/158 — reserved for future
       HeaderOnly,
       Unsupported,
   }
   ```

2. **SyncManager의 필터링 전략을 플러그인 가능하게 설계**: SyncManager가 bloom filter 전송과 merkleblock 수신 로직을 직접 포함하지 않고, 필터링 전략을 trait으로 분리한다.
   ```rust
   pub trait FilterStrategy: Send + Sync {
       fn filter_type(&self) -> SyncCapability;
       fn build_filter_message(&self, addresses: &[&str]) -> Vec<u8>;
       fn process_filtered_response(&self, data: &[u8]) -> Vec<H256>;
   }
   ```

3. **Peer service bit 확인 확장**: BIP157 피어는 `NODE_COMPACT_FILTERS(0x40)` 서비스 비트를 advertise한다. PeerManager가 이 비트를 인식하도록 상수를 미리 정의한다.
   ```rust
   pub const SERVICES_NODE_COMPACT_FILTERS: u64 = 0x40;
   ```

#### 왜 Phase 1에서 Neutrino를 구현하지 않는가

- BIP157/158은 서버 측에서 필터를 생성해야 하며, 현재 Bitcoin Core의 지원 수준이 BIP37만큼 보편적이지 않다.
- Phase 1의 목표는 "동작하는 SPV 동기화"를 빠르게 확보하는 것이다.
- 대신 설계 경계를 미리 분리해두면, Neutrino 추가 시 SyncManager/PeerManager를 대규모 리팩터링 없이 확장할 수 있다.

## 10. Phase 2: Wallet Manager

### Deliverable

- xpub 기반 주소 체인 관리
- external/internal gap limit 유지
- UTXO 집계
- wallet balance / tx history 계산
- rescan 및 restart recovery

### Wallet Shape

```rust
pub struct Wallet<C: WalletChain> {
    chain: C,
    master_xpub: ExtendedPubKey,

    external_cursor: u32,
    internal_cursor: u32,

    external_addresses: Vec<C::Address>,
    internal_addresses: Vec<C::Address>,

    used_addresses: HashSet<String>,
    known_addresses: HashSet<String>,

    utxos: HashMap<OutPoint, UtxoRecord>,
    transactions: HashMap<Txid, WalletTransaction>,

    balance: u64,
    total_received: u64,
    total_sent: u64,
    fee_rate: u64,
}
```

### Key Change From Original Draft

- UTXO 저장소는 기본적으로 `HashMap<OutPoint, UtxoRecord>`를 사용한다.
- 정렬은 coin selection 시점에 policy-aware view로 수행한다.
- 즉, 저장 구조와 selection 정책을 분리한다.

### Why Not `BTreeSet<Utxo>` As Primary Store

- UTXO 정렬 기준은 금액, age, spendability, confirmation 수 등 여러 정책에 따라 달라진다.
- primary storage를 정렬 자료구조로 고정하면 선택 정책을 바꾸기 어려워진다.

## 11. Persistence And Recovery

초안의 persistence는 너무 좁았기 때문에 복구 관점으로 다시 정의한다.

### 11-1. Required Persisted State

- known peers
- validated block headers or checkpoints after sync
- last synced height
- last fully applied wallet height
- address cursors
- known addresses
- wallet transactions
- UTXOs
- rescan hint metadata
- publish queue

### 11-2. Persistence Trait

```rust
pub trait Persistence: Send + Sync {
    fn load_peer_cache(&self) -> Result<Vec<PeerInfo>, PersistenceError>;
    fn save_peer_cache(&self, peers: &[PeerInfo]) -> Result<(), PersistenceError>;

    fn load_chain_state(&self) -> Result<Option<ChainState>, PersistenceError>;
    fn save_chain_state(&self, state: &ChainState) -> Result<(), PersistenceError>;

    fn load_wallet_state(&self) -> Result<Option<WalletState>, PersistenceError>;
    fn save_wallet_state(&self, state: &WalletState) -> Result<(), PersistenceError>;

    fn clear_wallet_state(&self) -> Result<(), PersistenceError>;

    /// Atomically persist a batch of headers together with chain state.
    ///
    /// This is critical for crash recovery: if the app crashes between
    /// writing headers and updating chain state, the DB ends up inconsistent
    /// (height updated but headers missing, or vice versa).
    ///
    /// Implementations should use a database transaction or equivalent
    /// atomic write mechanism. If atomic writes are not supported,
    /// the implementation must write headers first, then chain state,
    /// so that on recovery the worst case is "chain state behind headers"
    /// (recoverable by re-applying) rather than "chain state ahead of
    /// headers" (data loss).
    fn save_headers_batch(
        &self,
        headers: &[(u32, BlockHeader)], // (height, header) pairs
        chain_state: &ChainState,
    ) -> Result<(), PersistenceError>;

    /// Atomically persist wallet state with chain state after applying
    /// filtered blocks. Same atomicity rationale as save_headers_batch.
    fn save_sync_progress(
        &self,
        chain_state: &ChainState,
        wallet_state: &WalletState,
    ) -> Result<(), PersistenceError>;
}
```

### 11-2b. Atomicity Requirement

header sync 중 crash recovery를 올바르게 처리하려면 아래 두 조건이 필요하다:

1. **Headers + chain state**: N개 header와 chain state(last_height, last_hash)를 하나의 atomic operation으로 저장한다. 그렇지 않으면 height는 업데이트됐지만 해당 높이의 header가 없는 불일치 상태에 빠질 수 있다.

2. **Filtered blocks + wallet state**: merkleblock 처리 후 matched tx, UTXO 변경, wallet height를 원자적으로 업데이트한다. partial update는 잔액 불일치를 유발한다.

구현체가 SQLite를 사용하는 경우 트랜잭션으로 처리하고, key-value store를 사용하는 경우 write batch로 처리한다. `save_headers_batch`와 `save_sync_progress`가 이 원자성을 보장하는 메서드다.

### 11-3. Recovery Policy

- peer cache 손상 시 DNS seed로 재구성
- wallet state 손상 시 header state를 유지한 채 wallet rescan 허용
- chain state 손상 시 checkpoint부터 재동기화
- publish queue 복구 실패 시 재브로드캐스트 대신 상위 레이어에 확인 필요 상태를 전달

## 12. Event Model

콜백을 raw `void*` 스타일로 복제하지 않고 typed event로 바꾼다.

```rust
pub enum SyncEvent {
    PeerConnected(SocketAddr),
    PeerDisconnected(SocketAddr),
    SyncStarted { start_height: u32 },
    HeadersProgress { current_height: u32, target_height: u32 },
    FilteredBlockApplied { height: u32, matched_transactions: usize },
    CapabilityChanged(SyncCapability),
    SyncCompleted { height: u32 },
    SyncFailed(SyncError),
}

pub enum WalletEvent {
    BalanceChanged { new_balance: u64 },
    TransactionAdded { txid: Txid },
    TransactionUpdated { txid: Txid, block_height: Option<u32> },
    TransactionDeleted { txid: Txid, requires_rescan: bool },
}
```

### Event Principle

- sync와 wallet 이벤트를 분리한다
- FFI로 내릴 때도 타입 의미를 유지할 수 있도록 enum 중심으로 설계한다
- 이벤트는 상태 조회 API를 대체하지 않는다

## 13. Integration With Existing wallet-core

### Existing Relevant Structure

- `tw_utxo::UtxoContext`는 이미 UTXO 계열의 주소/트랜잭션/fee 구성을 담당한다.
- `chains/tw_bitcoin`은 이미 signer/planner/transaction util 경로를 갖고 있다.

### Integration Rule

- `tw_spv`는 직접 `CoinEntry`를 알 필요가 없다.
- `tw_wallet_manager`가 필요 시 `tw_utxo` primitive를 통해 transaction build/sign flow를 구성한다.
- 실제 Bitcoin chain wiring은 `chains/tw_bitcoin`에서 수행한다.

### Important Boundary Fix

초안의 `WalletManager<C: SpvContext>`와 `Wallet<C: UtxoContext>` 구조는 제네릭 경계가 맞지 않았다. 수정안에서는 아래처럼 역할을 분리한다.

```rust
pub struct WalletManager<S: SpvChain, W: WalletChain<Utxo = S::Utxo>> {
    spv_chain: S,
    wallet_chain: W,
    sync_manager: SyncManager<S>,
    wallet: Arc<RwLock<Wallet<W>>>,
    persistence: Arc<dyn Persistence>,
}
```

또는 Bitcoin only Phase 1에서는 더 단순하게 아래처럼 시작할 수 있다.

```rust
pub struct BitcoinWalletManager {
    sync_manager: SyncManager<BitcoinSpvChain>,
    wallet: Arc<RwLock<Wallet<BitcoinWalletChain>>>,
    persistence: Arc<dyn Persistence>,
}
```

권장 방향은 **public API는 concrete type으로 시작하고, 내부 구현만 generic하게 준비**하는 것이다.

## 17. Key Decisions

1. 초기 deliverable은 Bitcoin only다.
2. 구조는 BCash/Litecoin/Dogecoin 확장을 고려해 `SpvChain` / `WalletChain` 경계를 둔다.
3. BIP37은 시작점이지 최종 해법이 아니다.
4. BIP37 미지원 환경을 고려한 capability/fallback state를 반드시 둔다.
5. public API는 기존 signing API를 유지하고, wallet sync는 별도 선택 기능으로 추가한다.
6. runtime은 async 기반으로 구현하되 특정 runtime을 public API에 노출하지 않는다.
7. primary UTXO storage는 정렬 구조보다 key-value 구조를 우선한다.

---

## 18. Summary

이 설계는 breadwallet-core의 proven SPV 흐름을 Rust로 옮기되, 범위를 현실적으로 줄여서 **Bitcoin first**로 구현 가능하게 만드는 데 목적이 있다.

동시에 BCash/Litecoin/Dogecoin 확장을 위해 네트워크 규칙과 wallet 정책을 분리한 확장 포인트를 남긴다. 즉, 이 문서는 "처음부터 모든 체인을 일반화"하는 문서가 아니라, "Bitcoin을 먼저 제대로 만들고 이후 체인을 안전하게 추가"하기 위한 문서다.
